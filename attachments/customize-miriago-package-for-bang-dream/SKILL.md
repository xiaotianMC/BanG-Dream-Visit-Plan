# Customize MiriaGo Package For BanG Dream

本 Skill 是 **Plan MiriaGo Route 的上层自定义扩展**。

它不负责从零开始收集和规划 MiriaGo 数据，而是针对已经存在的巡礼包进行二次策划与维护。

核心目标不是单纯追求“最短路线”，而是在保持数据完整性和 MiriaGo 兼容性的基础上，使巡礼包：

* 更符合动画/作品中的移动路线；
* 更适合实际圣地巡礼；
* 更容易理解和使用；
* 具有统一的点位、片区和说明格式；
* 能够维护开放时间、票价、进入条件等现实信息；
* 能够保留完整来源和修改痕迹；
* 能够随着现实设施变化持续更新。

本 Skill 应与 `plan-miriago-route` 配合使用：

```text
Plan MiriaGo Route
        ↓
原始来源收集 / 导入 / 初步规划
        ↓
MiriaGo v2 数据包
        ↓
Customize MiriaGo Package
        ↓
人工策划 / 点位调整 / 片区整理 / 路线还原
        ↓
公共设施信息 / 巡礼说明 / 攻略
        ↓
最终巡礼包
```

# 0. Gate：强制交互与确认流程

本 Skill 必须采用 **Gate（确认闸门）** 工作流。Gate 的目的不是增加形式上的提问，而是防止 Agent 在用户尚未确认的情况下擅自改变巡礼包结构、路线或行程。

**任何 Gate 未通过时，不得进入下一阶段，不得通过默认值、推测或直接修改文件绕过确认。**

## Gate 0：巡礼背景与入境机场

开始进行实际路线规划、片区推荐或行程安排时，必须先询问：

```text
你从哪个机场入境日本？

A. 羽田机场（HND）
B. 成田机场（NRT）
C. 其他机场
D. 暂不确定
E. 跳过
```

### 羽田机场特殊规则

如果用户选择 **羽田机场**：

1. 检查当前邦多利巡礼包中是否存在羽田机场或羽田周边的邦多利巡礼点；
2. 将相关点位作为**可选推荐**主动告知用户；
3. 优先说明其适合作为**入境当天 / 离境当天顺路巡礼**的候选，而不是要求用户专程前往；
4. 必须明确这是推荐，不是强制行程；
5. 不得因为用户从羽田入境，就自动把羽田片区加入路线、改变原有片区顺序或压缩其他巡礼内容；
6. 只有用户明确接受后，才能将其纳入具体行程。

推荐表达：

```text
你从羽田机场入境的话，当前巡礼包中有「羽田机场」相关巡礼点。
如果你希望利用入境或离境的移动时间顺路巡礼，可以考虑把它安排进去。
这是可选项，不需要为了这个点位专程调整整体行程。
需要的话，我可以进一步帮你评估是否适合安排在入境当天。
```

如果用户选择 **成田、其他机场、暂不确定或跳过**：

* 不主动强行加入羽田巡礼；
* 不得因为存在羽田点位而要求用户修改机场；
* `跳过` 必须视为有效回答，不得反复追问机场。

## Gate 1：输入确认

必须确认：

```text
[ ] 当前 .sjhplan
[ ] 巡礼包名称
[ ] 当前版本
[ ] 修改目标
[ ] 是否允许修改点位
[ ] 是否允许调整片区
[ ] 是否允许调整路线
[ ] 是否需要同步 README / GUIDE
[ ] 是否需要同步公共设施信息
[ ] 是否需要保留原始来源
```

如果用户没有明确说明修改范围，先读取现有文件并形成提案，**不得直接大规模修改**。

## Gate 2：作品与来源确认

涉及新增作品、作品点位、Anitabi 数据或外部地图来源时：

```text
来源收集 / 导入
        ↓
来源结果复核
        ↓
用户确认
        ↓
进入自定义阶段
```

不得将 Agent 自行判断的作品归属、场景对应关系直接视为已确认事实。

## Gate 3：片区与路线确认

涉及以下操作时必须等待用户确认：

* 大规模调整片区；
* 大规模改变点位顺序；
* 改变动画行动路线；
* 删除或放弃远距离点位；
* 将可选点位纳入完整行程；
* 将羽田机场等远征点加入实际行程。

路线提案至少应区分：

```text
动画顺序
推荐巡礼顺序
现实效率方案
```

用户确认前只生成提案，不写入最终巡礼包。

## Gate 4：不可逆修改确认

以下操作必须获得用户明确确认：

```text
删除点位
删除作品
删除片区
删除图片
覆盖原 .sjhplan
大规模改变编号
大规模改变路线
删除来源
修改版权声明
```

原则：

> **新增可以提案，删除必须确认；原始文件永不覆盖。**

## Gate 5：最终发布确认

完成修改后必须执行：

```text
数据检查
↓
内容检查
↓
文档检查
↓
现实信息检查
↓
预览检查
↓
最终差异报告
↓
用户确认
↓
输出最终巡礼包
```

在最终确认之前，应优先输出 `customized-draft.sjhplan` 或等价草稿，不得直接宣称最终版本已经完成。


# 1. 核心设计理念


## 1.1 巡礼包不是单纯的地图数据

不要把巡礼包理解成：

```text
点位坐标 + 名称
```

而应理解为：

```text
作品资料
+
圣地点位
+
片区
+
推荐巡礼顺序
+
动画路线还原
+
现实交通
+
设施信息
+
拍摄注意事项
+
参考图片
+
攻略
```

因此任何修改都必须同时考虑：

1. MiriaGo 数据是否正确；
2. 点位在现实中的可访问性；
3. 点位与作品的关联；
4. 片区逻辑；
5. 推荐巡礼顺序；
6. 用户实际巡礼体验；
7. 相关说明文档是否同步。

---


## 1.2 BanG Dream 专用设计定位

本 Skill 虽然继承通用的 MiriaGo 巡礼包维护规则，但针对 **BanG Dream! 系列**必须额外考虑作品系列复杂、乐队作品跨度大、正片与 MV 巡礼并存、不同作品共享现实地点以及动画行动路线明显等特点。

### 1.2.1 作品体系必须分层管理

BanG Dream 巡礼包可以同时包含：

```text
全系列
├── 老邦七团
├── MyGO!!!!! / Ave Mujica
├── 梦限大
├── 其他正片内容
└── MV / 特殊歌曲巡礼
```

必须根据现有 README 中的作品分类维护作品映射，不得因为现实地点相同就错误合并作品归属。

当前项目的设计以**全收录**为目标，同时通过核心、推荐、可选等方式降低实际巡礼压力。

### 1.2.2 正片巡礼与 MV 巡礼分开管理

必须明确区分：

```text
正片场景
MV场景
特殊歌曲场景
```

当前项目采用：

```text
正片巡礼 → 数字编号
MV巡礼 → 字母 + 数字编号
```

其中 MyGO!!!!! MV 使用 `A1～An`，其他乐队使用对应字母编号。

如果某些歌曲因项目既定规则被纳入正片巡礼包，则不得擅自重新归类为 MV 补充包。

### 1.2.3 BanG Dream 点位必须尽量记录作品关联

新增或修改点位时，优先确认：

```text
作品 / 乐队
EP / 集数
场景时间
角色
具体行动
MV
其他官方作品资料
```

推荐：

```text
EP03
祥子与睦经过此处
```

而不是：

```text
感觉这里应该是圣地
```

无法确认具体集数或场景时，应标记为待确认，不得自行补全。

### 1.2.4 “动画行动路线”是邦多利巡礼的重要特征

BanG Dream 巡礼不应只按照地理距离排序。

如果角色在动画中连续经过多个现实地点，应优先保留这种移动关系：

```text
角色行动
↓
场景 A
↓
场景 B
↓
场景 C
```

即使现实中存在更短路线，也不得在未说明的情况下直接替换。

当前项目明确以**还原动画中的场景移动路线**为核心目标，并在确保整体行程可执行的前提下尽可能还原作品路线。fileciteturn0file2L15-L17

### 1.2.5 “全收录”不等于“全部必须巡礼”

BanG Dream 点位数量可能较多，因此必须同时维护：

```text
完整收录
核心点位
推荐点位
可选点位
```

“可选”主要根据：

```text
剧中重要程度
交通便利程度
拍摄价值
现实可访问性
```

进行判断。

不得因为某点位属于可选，就直接删除；也不得因为点位存在，就让用户认为必须前往。

项目现有规则已经明确使用“可选”标记来降低实际行程压力。

### 1.2.6 梦限大 OP 特殊点位

`●` 标记的点位属于梦限大 OP 的飞碟飞行路径。

此类点位：

* 可以完整保留；
* 不要求全部纳入普通巡礼路线；
* 应说明拍摄还原难度；
* 可根据用户是否追求高还原度决定是否推荐。

项目现有 README 已将这类点位定义为可选择性巡礼内容。

### 1.2.7 同一现实地点的多作品关联

BanG Dream 中可能出现：

```text
同一现实地点
+
不同乐队
+
不同 EP
+
不同作品
```

此时不得因为坐标相同就简单删除其中一个关联。

应优先：

```text
保留现实地点
+
保留全部作品关联
+
必要时拆分逻辑点位
+
在备注中说明不同场景
```

只有在巡礼方式、作品关联和信息需求均完全相同的情况下，才考虑合并。

### 1.2.8 车站、街道、商店街等“日常场景”优先保证可执行性

BanG Dream 大量场景属于：

```text
车站
街道
商店街
公园
学校周边
商业设施
住宅区周边
```

这些地点通常不是传统意义上的“景点”。

因此说明重点应放在：

```text
从哪里进入
具体拍摄位置
是否需要进入站内 / 店内
是否需要购票
什么时候适合拍摄
是否容易影响行人
```

而不是泛泛介绍设施本身。

### 1.2.9 商业设施与粉丝消费内容不得混淆

如果一个地点同时具有：

```text
动画取景价值
+
BanG Dream 官方 / 联动店铺 / 周边购买价值
```

应分别说明：

```text
巡礼价值
消费 / 购物价值
```

不要因为存在官方店铺或联动活动，就把普通商业地点自动提高为核心圣地。

### 1.2.10 临时活动与固定圣地点位分离

如果点位来源于：

```text
期间限定活动
联动活动
临时展览
Live / Event
限定装饰
```

必须明确标记其时效性。

不得把一次性活动的现实布置写成长期存在的固定场景。

### 1.2.11 邦多利巡礼推荐应允许“顺路型”推荐

对于：

```text
机场
车站
远距离片区
国内远征点
```

尤其应优先考虑：

```text
顺路巡礼
入境顺路
离境顺路
换乘顺路
观光顺路
```

而不是默认要求用户专程前往。

其中羽田机场是明确的**推荐候选点**：只有当用户入境机场为羽田时才主动提示，并始终保持可选，不得强行加入行程。

# 2. 与 Plan MiriaGo Route 的职责边界

## Plan MiriaGo Route 负责

* Bangumi 作品搜索；
* Anitabi 数据导入；
* Google My Maps / KML / KMZ 导入；
* 初始点位合并；
* 来源去重；
* 坐标验证；
* 初始区域聚类；
* 道路网络路线计算；
* 初始路线提案；
* MiriaGo v2 数据包创建。

## Customize MiriaGo Package 负责

* 修改已有点位名称；
* 修改点位描述；
* 调整点位顺序；
* 调整片区归属；
* 合并或拆分片区；
* 添加人工整理点位；
* 添加动画非 Anitabi 场景；
* 添加 MV 场景；
* 调整编号；
* 修改巡礼说明；
* 添加公共设施信息；
* 添加交通说明；
* 添加开放时间、票价等现实信息；
* 整理参考图片；
* 维护 README / GUIDE / attachments；
* 检查内容一致性；
* 检查巡礼包整体体验。

如果任务涉及**新的外部来源导入**，优先调用 `plan-miriago-route`，完成来源确认后再进入本 Skill。

# 3. 输入检查点

开始修改之前必须确认：

* 当前 `.sjhplan` 文件；
* 巡礼包名称；
* 当前版本；
* 修改目标；
* 是否允许修改点位；
* 是否允许调整片区；
* 是否允许调整路线；
* 是否需要同步 Markdown 文档；
* 是否需要更新公共设施信息；
* 是否需要保留原始来源；
* **入境日本的机场**（羽田 / 成田 / 其他 / 暂不确定 / 跳过）；如选择羽田，需进一步确认是否希望将羽田相关巡礼作为顺路候选。

如果用户只是说：

> “帮我优化这个巡礼包”

不得直接修改。

必须先检查当前巡礼包结构，并向用户总结：

```text
作品：
点位数量：
片区数量：
已有说明文件：
公共设施信息：
路线数据：
参考图片：
```

然后明确需要优化的范围。

# 4. 巡礼包结构检查

修改任何内容之前，应检查：

```text
.sjhplan
├── 作品
├── 点位
├── 片区
├── 路线
├── 备注
├── 图片
└── 其他资源
```

以及仓库中的：

```text
README.md
GUIDE.md
attachments/
    公共设施信息.md
    ...
```

不得因为修改某一个点位而删除与其无关的资源。

必须保留：

* 未修改点位；
* 原始完成状态；
* 原有图片；
* 原有备注；
* 未知 JSON 字段；
* 未知 ZIP 条目；
* 用户手动添加的内容。

# 5. 点位自定义规则

## 5.1 点位名称

优先保证：

```text
容易搜索
容易理解
与现实地点对应
与作品场景对应
```

推荐格式：

```text
现实地点
```

或者：

```text
现实地点（具体设施）
```

例如：

```text
JR目白站
东京站
东京站（东北新干线21号站台）
旧古河庭园
旧古河邸
```

如果同一现实地点存在多个完全不同的巡礼场景，应拆成多个逻辑点位，而不是强行合并。

例如：

```text
东京站
东京站（东北新干线21号站台）
```

---

# 6. 点位说明规则

点位说明必须优先回答：

> “巡礼者到了这里以后，需要知道什么？”

推荐按照以下顺序组织：

```text
① 是否需要进入
② 具体取景位置
③ 是否需要购票
④ 开放时间限制
⑤ 拍摄注意事项
⑥ 作品还原度
⑦ 可选行为
```

例如：

```markdown
> 拍摄巡礼图**需要进入站内区域**，主要取景点位于站台上。

**巡礼注意**

拍摄时请注意不要影响其他乘客通行。
```

---

# 7. “需要进入 / 无需进入”必须明确

这是巡礼包的重要信息。

每一个设施类点位，都应该尽可能明确：

### 无需进入

```text
拍摄巡礼图无需进入馆内，店外即可取景。
```

### 需要进入

```text
拍摄巡礼图需要进入设施内部，取景点位于馆内。
```

### 部分需要进入

```text
点位分布在检票口外和检票口内，具体取景位置请根据点位说明确认。
```

### 可选进入

```text
拍摄巡礼图无需进入馆内；如对设施本身感兴趣，可以根据开放情况选择入馆。
```

不要让用户到了现场才发现需要购票或无法进入。

---

# 8. 作品还原度

对于现实场景与动画差异较大的地点，应主动说明。

推荐：

```markdown
> 动画中的场景与现实地点并非完全还原，是否专程前往可根据个人兴趣决定。
```

对于：

* 低还原度；
* 仅有部分元素对应；
* 外观变化较大；
* 已经改装；
* 已经关闭；

必须明确标注。

不得因为“Anitabi 有点位”就默认该点位具有较高巡礼价值。

---

# 9. 全收录原则

本巡礼包以**全收录**为重要目标。

因此：

> “巡礼价值较低” ≠ “应该删除”。

如果点位与作品存在明确关联，但：

* 还原度低；
* 距离较远；
* 交通不便；
* 进入困难；

优先考虑：

```text
保留点位
+
降低推荐优先级
+
添加说明
```

而不是直接删除。

只有以下情况才建议删除：

* 确认来源错误；
* 坐标错误且无法修正；
* 与作品没有实际关联；
* 明确重复且没有独立巡礼意义；
* 用户明确要求删除。

---

# 10. 片区设计

片区不是单纯按照地图距离划分。

应综合考虑：

```text
地理位置
+
交通方式
+
动画行动路线
+
作品关联
+
实际巡礼时间
+
设施开放时间
```

例如：

```text
同一地区
```

不一定意味着应该属于同一个片区。

如果两个点之间：

* 步行时间过长；
* 中间需要换乘；
* 作品行动路线不同；
* 开放时间差异明显；

可以拆分。

---

# 11. 片区命名

优先使用用户容易理解的现实地名：

```text
池袋
秋叶原
目白
大塚
五反田
东京站
```

必要时使用：

```text
池袋—SunshineCity
东京站—丸之内
小豆岛—土庄
逗子—叶山
```

避免使用：

```text
区域A
区域B
Group 01
Cluster 02
```

除非这些只是内部临时名称。

---

# 12. 片区编号

如果项目已经建立编号体系，修改时必须保持一致。

推荐：

```text
01
02
03
...
```

对于 MV：

```text
A1
A2
A3
...
```

不同作品可以使用不同字母体系。

不要因为重新排序而随意改变已经公开使用的编号。

如果确实需要改变编号，应检查：

* README；
* GUIDE；
* 公共设施信息；
* 图片文件名；
* 路线说明；
* 外部引用。

---

# 13. 路线设计优先级

本巡礼包的路线不是单纯追求最短距离。

优先级：

```text
① 能够实际执行
② 尽可能还原动画行动路线
③ 减少无意义折返
④ 合理利用交通
⑤ 合理控制步行距离
⑥ 最短距离
```

也就是说：

> **动画路线还原优先于纯数学意义上的最短路线。**

但如果动画路线导致：

* 极端折返；
* 大量无意义步行；
* 明显增加旅行成本；
* 现实中无法执行；

则应提出替代方案。

推荐：

```text
动画顺序：
A → B → C → D

现实推荐：
A → B → D → C

理由：
减少约 XX 分钟步行。
```

不得在没有说明的情况下改变作品顺序。

---

# 14. 路线优化

路线修改必须区分：

### 动画顺序

角色在作品中的实际行动顺序。

### 推荐巡礼顺序

考虑现实交通后的建议顺序。

### 最短路线

单纯根据道路网络计算的最优路线。

三者不能混为一谈。

如果用户要求：

> “尽可能还原动画”

应优先保持动画顺序。

如果用户要求：

> “帮我规划最省时间路线”

才可以优先进行现实路线优化。

---

# 15. 点位顺序修改

修改点位顺序时必须检查：

```text
片区内部顺序
↓
片区之间顺序
↓
交通
↓
开放时间
↓
动画顺序
```

如果某个点位有明确开放时间限制：

```text
09:00～17:00
```

而同片区其他地点全天开放，则应考虑将其安排在合适时段。

---

# 16. 公共设施信息

`attachments/公共设施信息.md` 是巡礼包的重要组成部分。

它不是普通的附加说明，而是：

> **巡礼行程可执行性数据库的文字呈现。**

公共设施信息建议包含：

```text
设施名称
地址
官方网站
开放时间
休馆日
入馆/入场费用
巡礼进入条件
特殊规定
巡礼注意
信息更新时间
```

当前项目已经采用这种方式维护设施信息，例如永青文库会分别说明开放时间、休馆日、票价和巡礼注意事项。

---

# 17. 公共设施信息的时效性

所有开放时间、票价和营业状态都属于：

```text
高时效信息
```

因此必须避免写成绝对结论。

优先：

```text
以官方公告为准
```

而不是：

```text
永远是 XX:XX～XX:XX
```

必须保留类似：

```markdown
> 实际开放时间可能根据日期、活动及设施情况调整，请以官方信息为准。
```

项目已有统一的信息时效性声明：

```text
部分内容可能存在滞后或与实际不一致的情况。
```

并建议出发前确认最新信息。

不要在单个设施中重复制造与总声明矛盾的信息。

---

# 18. 设施信息来源优先级

优先级：

```text
官方官网
↓
官方运营机构
↓
地方政府
↓
铁路/交通运营商
↓
官方社交媒体
↓
可靠的现场资料
↓
用户提供信息
↓
第三方网站
```

如果用户提供了明确的信息：

```text
来源类型：user_confirmed
```

不得伪装成官方资料。

---

# 19. 交通信息

交通信息必须注明来源。

例如：

```markdown
**交通参考：**
JR东日本官方时刻表
```

不得自行编造：

* 列车时刻；
* 票价；
* 首末班车；
* 临时停运；
* 施工信息。

如果只是估算：

```text
预计
约
参考
```

必须明确标注。

---

# 20. 车站巡礼特殊规则

车站类点位需要额外检查：

```text
是否需要进入检票区
是否需要乘车
是否可以购买入场券
是否需要站内换乘
站台方向
是否存在站台间无法互通
```

例如末广町站需要特别说明不同站台对应不同方向，并且站台之间没有站内连通通道。

对于：

```text
东京站
新宿站
池袋站
涩谷站
```

等大型车站，应尽可能提供：

```text
线路
站台
检票口
出口
换乘方向
```

---

# 21. 公园类点位

公园不能简单写：

```text
24小时开放
```

必须检查：

```text
公园整体开放时间
具体区域开放时间
设施开放时间
儿童专用时间
夜间关闭
临时关闭
```

例如荒川自然公园不同区域存在不同闭园时间，因此必须根据具体点位所在区域判断。

---

# 22. 商业设施

商业设施应区分：

```text
建筑开放时间
商店营业时间
餐厅营业时间
具体店铺营业时间
巡礼点实际可进入时间
```

不能直接使用：

```text
商场营业时间 = 巡礼点开放时间
```

例如表参道HILLS的巡礼点位位于建筑内部，因此需要在设施开放时间内进入，但具体店铺及公共区域仍可能存在差异。

---

# 23. 图片管理

参考图片分为：

```text
Anitabi 原图
Anitabi 缩略图
外部来源图片
用户提供图片
项目自行制作图片
```

不得改变图片来源归属。

不得为了“统一风格”覆盖原始参考图片。

如果需要增加图片：

```text
保留原图
+
新增图片
```

除非用户明确要求替换。

---

# 24. 图片命名

推荐：

```text
{point-id}_{index}.{ext}
```

例如：

```text
point-001_01.jpg
point-001_02.jpg
```

如果项目已经存在命名规则，必须沿用已有规则。

---


# 25. 版权与来源

不得把第三方资料写成原创资料。

对于：

```text
Anitabi
Bangumi
Google My Maps
Bilibili
个人贡献者
官方设施
```

应保留来源。

尤其是参考图片：

```text
图片来源 ≠ 点位来源
```

必须分别处理。

项目现有版权声明明确指出：

* 巡礼包采用 CC BY-NC-SA 4.0；
* 部分点位和参考图来自 Anitabi；
* 点位、截图、图片及元数据版权归原平台、贡献者或权利方；
* 项目对部分点位名称、图片和备注进行了统一及修改。

不得因为修改内容而删除这些信息。

---

# 26. 自定义点位

如果用户要求：

> “增加一个动画里出现、但 Anitabi 没有的地方”

可以创建自定义点位。

必须记录：

```text
point source = custom
```

并至少具有：

```text
名称
坐标
作品
关联说明
来源
```

来源可以是：

```text
动画截图
官方资料
用户提供
实地确认
公开地图
```

不得把自定义点位伪装成 Anitabi 点位。

---

# 27. 自定义点位的作品关联

新增点位时必须回答：

```text
为什么它属于这个作品？
```

优先记录：

```text
EP
时间
场景
角色
MV
漫画
官方设定
```

例如：

```text
EP03
祥子与睦经过此处
```

而不是：

```text
感觉这里应该是圣地
```

---

# 28. 点位合并

只有在以下情况下才合并：

* 实际地点完全相同；
* 巡礼方式完全相同；
* 没有独立的作品关联；
* 合并不会损失重要信息。

如果：

```text
同一建筑
```

但：

```text
不同楼层
不同入口
不同检票区域
不同作品场景
```

则应保留独立点位。

---

# 29. 点位拆分

出现以下情况时建议拆分：

```text
同一现实设施
+
不同进入条件
```

例如：

```text
东京站
东京站（东北新干线21号站台）
```

前者可能只需要进入普通站内区域，而后者涉及新干线区域和入场券，因此必须独立说明。

---

# 30. 路线与开放时间联动

如果点位存在开放时间：

```text
A：09:00～17:00
B：全天
C：10:00～20:00
```

路线规划时应优先保证：

```text
A / C
```

处于开放时间内。

不得仅依据地理距离排序。

---

# 31. 巡礼优先级

可以为点位建立内部优先级：

```text
S：核心圣地
A：推荐
B：可选
C：低优先级
```

但如果当前 MiriaGo 数据格式没有对应字段：

> 不得擅自向 schema 中添加未经支持的字段。

可以将优先级写入备注或 Markdown 文档。

---

# 32. “核心巡礼”与“完整巡礼”

推荐将巡礼包设计为：

```text
完整收录
```

同时通过：

```text
核心点位
推荐点位
可选点位
```

降低完整数据对实际旅行者造成的压力。

这样既可以保持：

> 全收录

又可以避免用户认为：

> 504 个点全部必须巡礼。

---

# 33. 路线说明

推荐使用：

```markdown
### 推荐顺序

1. A
2. B
3. C
4. D

> 本顺序主要参考动画中的行动路线，并结合现实交通进行了调整。
```

如果路线纯粹为了效率：

```markdown
> 本路线以现实交通效率为优先，并非完全按照动画中的移动顺序。
```

必须明确说明路线设计目标。

---

# 34. 动画还原型路线

如果用户要求：

> “按照动画走”

则优先级为：

```text
动画顺序
>
现实效率
```

允许存在：

```text
折返
非最短路线
额外步行
```

但如果代价明显，应主动提示。

---

# 35. 实用型路线

如果用户要求：

> “帮我安排一天能走完”

则优先：

```text
开放时间
+
交通
+
步行距离
+
景点密度
+
休息
```

此时可以改变动画顺序，但必须注明：

```text
为了实际巡礼效率进行了调整。
```

---

# 36. 海外 / 国内远征

对于：

```text
东京及周边
国内远征
海外
```

等不同区域，应允许使用不同的路线策略。

例如：

```text
东京：
公共交通 + 步行

小豆岛：
公交 + 船 + 步行

海外：
机场 + 公共交通 + 步行
```

不要使用统一的东京步行逻辑处理所有地区。

现有交互地图也已经按照“东京及周边 / 国内远征 / 海外”进行区域筛选，因此自定义 Skill 应保持这种区域级组织思路。

---

# 37. 远距离点位

不得因为点位距离远就自动删除。

应该标记：

```text
远征点
独立区域
需要额外交通
建议单独安排
```

例如：

```text
小豆岛
羽田机场
关岛
```

可以成为独立片区。

# 50. 核心原则总结

始终遵循以下原则：

> **数据完整性优先于路线优化。**

> **动画路线还原优先于单纯最短路线。**

> **实际可执行性优先于理论最优。**

> **保留低价值点位，而不是轻易删除。**

> **现实信息必须具有来源和时效性意识。**

> **删除必须经过确认。**

> **原始数据永不覆盖。**

> **MiriaGo 数据、README、GUIDE、公共设施信息必须保持一致。**

> **用户提供的信息必须保留其来源属性。**

> **任何无法确认的信息都必须明确标记为待确认，而不是自行补全。**

> **巡礼包的目标不是“生成一张地图”，而是生成一套可以真正帮助用户完成圣地巡礼的资料。**
